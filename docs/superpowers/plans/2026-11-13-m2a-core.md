# Milestone 2a — Core in Java puro con test: piano di implementazione

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** il pacchetto `com.toxineren.exoframes.core` implementa energia, consumo per azione, pezzi con durabilità e stati, ripartizione del danno, tier, moduli e il modello di config, senza alcun import di Minecraft, con test JUnit 5 verdi su tutte e quattro le varianti.

**Architecture:** `core/` è una libreria di regole pure: tipi immutabili o piccoli oggetti mutabili con metodi deterministici, numeri interi per l'energia (RE) con accumulo in millesimi per i consumi frazionari per tick, enum per pezzi/tier/moduli, un `ExoframesConfig` POJO con i default della spec che alimenta tutte le costanti (niente numeri magici nelle classi). Le milestone successive (compat, entità, HUD) consumano queste API; qui nulla sa cosa sia un `ItemStack`.

**Tech Stack:** Java 17 (il codice deve compilare con `--release 17` per 1.20.1), JUnit Jupiter 5.11.x, Gradle `test` task per variante (`:1.21.1-neoforge:test` è il riferimento; CI esegue il test su tutte e quattro).

**Spec:** `docs/superpowers/specs/claude-doc-2026-11-04-redstone-exoframes.md` (sezioni "Il telaio", "Pezzi, danni e riparazione", "Sistema energetico", "Tier e progressione", "Moduli") e `docs/superpowers/specs/2026-11-12-redstone-exoframes-design.md` (§5.1 layout, §5.4 modello dati, §7 decisioni).

## Global Constraints

- Nessun import di `net.minecraft.*`, `net.fabricmc.*`, `net.minecraftforge.*`, `net.neoforged.*`, `dev.architectury.*`, `com.google.gson.*` in `com.toxineren.exoframes.core` (`tools/check_sources.sh` lo verifica).
- Tutti i valori numerici vengono da `ExoframesConfig` con i default della spec: cella 10.000 RE; consumi fermo 2 RE/s, cammino 8 RE/s, sprint 20 RE/s, salto 15 RE; soglia energia bassa 10%; a zero: velocità −70%, protezione 50%; malus velocità telaio −15%; quote protezione elmo 15%, torso 30%, braccia 12,5% ciascuno, gambe 15% ciascuna; slot moduli base 1/2/1/1/1/1; stati visivi: danneggiato ≤50%, critico <15%, rotto 0; torso rotto consumo +25%; gamba rotta velocità −15%; tier: slot extra 0/+1/+2/+2/+3, protezione relativa al ferro 1,00 / 1,333 / 1,733 / 1,60 / 2,00; moduli e costi come da tabella della spec; kit di riparazione +25%; 20 tick al secondo.
- Energia sempre `int` in RE; i consumi per tick si accumulano in millesimi di RE (`milliRe`) senza perdita: 2 RE/s = 100 milliRE/tick.
- Identificatori in inglese (`scrap`, `industrial`, `armored`, `netherite`, `prototype`; `jetpack`, `shockwave`, `night_vision`, `scanner`, `rebreather`, `hydraulic_blade`, `drill`, `energy_shield`, `sculk_detector`, `servos`); testi in italiano solo nei file di lingua, mai nel core.
- Un commit per task, push dopo ogni commit.

## Review Focus

1. Consumi frazionari (2 RE/s = 0,1 RE/tick) arrotondati per tick: con `int` nudo il telaio fermo non consumerebbe mai. Atteso: dopo 20 tick fermo la cella ha perso esattamente 2 RE. Test in Task 3 (`EnergyMeterTest.idleTwentyTicksDrainsTwoRe`).
2. Cella che scende sotto zero o oltre la capacità per un drain/charge grande. Atteso: clamp a [0, capacity] e `drain` restituisce quanto ha davvero tolto. Test in Task 2.
3. Danno ripartito su pezzi tutti rotti o telaio senza pezzi: divisione per zero o `NaN`. Atteso: nessuna eccezione, danno assorbito 0, tutta la quota va "al giocatore". Test in Task 5.
4. Modulo "gambe (entrambe)" con una sola gamba montata o una gamba rotta: l'onda d'urto non deve attivarsi. Test in Task 9 (`FrameRulesTest.shockwaveNeedsBothLegs`).
5. Config con valori fuori range (quote che non sommano a 1, soglie negative): `validate()` deve normalizzare o rifiutare in modo prevedibile, non produrre protezioni >100%. Test in Task 8.
