# Milestone 2b — Interfacce `compat/` con implementazioni 1.20.1 e 1.21.1: piano di implementazione

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** il pacchetto `com.toxineren.exoframes.compat` espone le sei interfacce che chiudono tutte le differenze tra 1.20.1 e 1.21.1 e tra i loader di cui la milestone 3 ha bisogno (dati sugli item, materiali armatura, rete, attributi, classificazione del danno, stato del telaio per giocatore), ciascuna compilata e verificata con `javap` su tutte e quattro le varianti, senza che nessun `//? if` esca da `compat/` e `platform/`.

**Architecture:** il Task 1 chiude tre lacune del core emerse dalla revisione finale di M2a (condizioni dei moduli, costi a tenuta/uso, riporto frazionario del danno) prima che il codec fissi la forma dello stato; poi una interfaccia per tema in `compat/`, con una sola classe di implementazione per tema che contiene le condizioni Stonecutter di versione (`//? if >=1.21`) e, dove serve, di loader (`//? if fabric`), così che `content/`, `entity/`, `block/`, `item/` e `client/` chiamino solo l'interfaccia. Lo stato del telaio per giocatore vive in un `SavedData` del server (mappa UUID → NBT) e viene sincronizzato al client con un pacchetto `Net`: una sola implementazione per i quattro target, niente capability Forge, attachment NeoForge o data-attachment Fabric. I dati degli item viaggiano come un `CompoundTag` con schema fisso: nel tag dello stack su 1.20.1, nel componente `minecraft:custom_data` su 1.21.1, con accesso tipizzato dall'interfaccia.

**Tech Stack:** come M1/M2a (Stonecutter 0.9.8, Architectury Loom 1.17.493, Architectury API 9.2.14 / 13.0.11, Fabric API 0.92.12 / 0.116.18, Forge 47.4.29, NeoForge 21.1.266, JDK 21, bytecode 17/21). Verifica: compilazione delle quattro varianti + `javap -c -p` sulle classi compilate per confermare quale ramo è attivo in ogni variante.

**Spec:** `docs/superpowers/specs/2026-11-12-redstone-exoframes-design.md` (§5.2 interfacce, §5.4 modello dati del telaio, §7 decisioni) e `docs/audit/mjolnir-armor-audit.md` §3 (hook Forge e loro equivalenti) e §4 (API vanilla che cambiano, con le interfacce proposte).

## Global Constraints

- Nessun import di `net.minecraft.*`, `net.fabricmc.*`, `net.minecraftforge.*`, `net.neoforged.*`, `dev.architectury.*`, `com.google.gson.*` in `com.toxineren.exoframes.core`.
- Commenti condizionali Stonecutter (`//? if ...`) solo in `com.toxineren.exoframes.compat` e `com.toxineren.exoframes.platform`; il resto del codice chiama solo le interfacce di `compat/`.
- Ogni interfaccia di `compat/` ha una sola implementazione concreta (`...Impl`), scelta staticamente via `Compat.<nome>()`; le classi di `content/entity/block/item/client` non istanziano le implementazioni.
- Schema NBT dei dati item (chiavi esatte, tutte sotto un tag radice `exoframes`): `energy` (int), `tier` (string id del tier), `durability` (int), `max_durability` (int), `modules` (list di string id), `color_primary` (int RGB), `color_secondary` (int RGB), `owner` (UUID come int array), `unlocked` (boolean), `reinforced` (boolean), `cell` (tag annidato con `energy`), `pieces` (tag con una voce per `PieceSlot` id in minuscolo), `stowed` (list di tag item).
- Identificativi di rete: `redstone_exoframes:frame_state_sync` (S2C), `redstone_exoframes:module_toggle` (C2S), `redstone_exoframes:frame_exit` (C2S), `redstone_exoframes:cell_swap` (C2S). Ogni pacchetto C2S viene validato sul server (giocatore nel telaio, modulo montato) prima di agire.
- Id degli `AttributeModifier` (1.21.1 `ResourceLocation`, 1.20.1 UUID derivato in modo stabile con `UUID.nameUUIDFromBytes(id.toString().getBytes(UTF_8))`): `redstone_exoframes:frame_speed`, `redstone_exoframes:frame_knockback`, `redstone_exoframes:frame_armor`, `redstone_exoframes:frame_toughness`.
- Ogni task termina con compilazione delle quattro varianti, `bash tools/check_sources.sh` → `OK sources`, commit sul branch del piano e push.
- Prerequisiti da M2a: `Tier.byId(String)`, `ModuleType.byId(String)` (se M2a Task 7 non lo ha aggiunto, aggiungerlo nel Task 3 di questo piano con un test in `ModuleTypeTest`), `FrameState`, `FrameEffects`, `DamageKind`, `PieceSlot`, `ExoframesConfig`.
- Fuori da questo piano (arrivano con i loro consumatori in M3/M4): le classi base `compat/CompatBlockEntity`, `compat/CompatEntityBlock`, `compat/CompatEntity`, le basi client (`CompatContainerScreen`, basi GeckoLib, `ClientTiming`), `LootHooks` (M6) — vedi audit §4.

## Review Focus

1. Un `//? if` dimenticato fuori da `compat/`/`platform/`, o un'implementazione importata direttamente da `content/`: compila sulla variante attiva e si rompe sulle altre o viola l'architettura. Test: `tools/check_sources.sh` (già fallisce sulle condizioni fuori posto) esteso con il divieto di importare `com.toxineren.exoframes.compat.impl` fuori da `compat/` (Task 2).
2. Dati item letti su una variante e scritti sull'altra con chiavi diverse: i mondi 1.20.1 aggiornati a 1.21.1 perderebbero energia e durabilità. Atteso: stesso `CompoundTag` su entrambe. Test: Task 3 verifica con `javap` che entrambe le implementazioni usano le stesse costanti di chiave (una sola classe `NbtKeys`).
3. `AttributeModifier` applicato due volte (login + cambio dimensione) perché l'id non è stabile tra sessioni: velocità che si accumula. Atteso: id deterministici e `removeModifier` prima di `addPermanentModifier`/`addTransientModifier`. Test: Task 6 verifica con `javap` l'uso di `UUID.nameUUIDFromBytes` sulla 1.20.1 e di `ResourceLocation` sulla 1.21.1, e il codice chiama sempre `remove` prima di `add`.
4. `SavedData` non marcato `setDirty()` dopo una modifica: lo stato del telaio si perde al riavvio del server. Atteso: ogni mutazione passa da `FrameStateAccess.update(player, Consumer<FrameState>)` che chiama `setDirty()`. Test: Task 8 asserisce con `grep`/`javap` che l'unico punto di scrittura chiama `setDirty`.
5. Pacchetto C2S fidato: un client modificato attiva moduli non montati o esce dal telaio di un altro. Atteso: validazione sul server. Test: Task 7 include nel gestore la validazione e `check_sources.sh` verifica che ogni `registerC2S` abbia un handler che chiama `FrameStateAccess`.
