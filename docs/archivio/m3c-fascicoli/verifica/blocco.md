## 1. API differences between 1.20.1 and 1.21.1 (and loader patches)

### 1.1 The block class
- `EntityBlock` is identical on both [javap V120, V121]: `BlockEntity newBlockEntity(BlockPos, BlockState)` (abstract); `default <T extends BlockEntity> BlockEntityTicker<T> getTicker(Level, BlockState, BlockEntityType<T>)`; `BlockEntityTicker.tick(Level, BlockPos, BlockState, T)`.
- `BaseEntityBlock` [javap four]: `getRenderShape(BlockState)` returns `RenderShape.INVISIBLE` on all four; 1.21.1 adds `protected abstract MapCodec<? extends BaseEntityBlock> codec()`; `protected static <E extends BlockEntity, A extends BlockEntity> BlockEntityTicker<A> createTickerHelper(BlockEntityType<A>, BlockEntityType<E>, BlockEntityTicker<? super E>)` on both.
- `Block` [javap four]: constructor `public Block(BlockBehaviour.Properties)`. On 1.21.1 `BlockBehaviour.codec()` is abstract but `Block.codec()` is concrete (`protected MapCodec<? extends Block> codec()` returns `Block.CODEC`). `BlockBehaviour.getRenderShape` returns `RenderShape.MODEL` on all four. **A class `extends Block implements EntityBlock` therefore needs neither `codec()` nor a `getRenderShape` override on any variant.**
- `HorizontalDirectionalBlock` [javap V120, V121]: `public static final DirectionProperty FACING`; on 1.21.1 it also has an abstract `codec()`. Extending it costs a versioned method; declaring the property on a plain `Block` does not (1.6).
- Visibility: every `BlockBehaviour` hook named below is `public` on 1.20.1 (V120, F120) and `protected` on 1.21.1 (V121, N121) [javap four]. An override declared `public` compiles on both. Code outside the class must go through `BlockState`, never `block.hook(...)`.
- Hooks with the **same** parameters on both: `void onRemove(BlockState, Level, BlockPos, BlockState, boolean)`, `void onPlace(BlockState, Level, BlockPos, BlockState, boolean)`, `void neighborChanged(BlockState, Level, BlockPos, Block, BlockPos, boolean)`, `boolean hasAnalogOutputSignal(BlockState)`, `int getAnalogOutputSignal(BlockState, Level, BlockPos)` (defaults `false`/`0`), `BlockState rotate(BlockState, Rotation)`, `BlockState mirror(BlockState, Mirror)`; on `Block`: `public BlockState getStateForPlacement(BlockPlaceContext)`, `protected void createBlockStateDefinition(StateDefinition.Builder<Block, BlockState>)`, `protected final void registerDefaultState(BlockState)`, `public static void popResource(Level, BlockPos, ItemStack)`.
- Hooks that **differ** (avoid overriding): `playerWillDestroy(Level, BlockPos, BlockState, Player)` returns `void` on 1.20.1 and `BlockState` on 1.21.1; `appendHoverText(ItemStack, BlockGetter, List<Component>, TooltipFlag)` vs `(ItemStack, Item.TooltipContext, List<Component>, TooltipFlag)` [javap V120, V121].

- How the game calls it [javap `ServerPlayerGameMode.useItemOn(ServerPlayer, Level, ItemStack, InteractionHand, BlockHitResult)` V120 offset 139, V121 offsets 136-197; `MultiPlayerGameMode.performUseItemOn` V120, V121]: once per hand, on client and server alike; skipped when `player.isSecondaryUseActive()` and either hand holds something (sneaking with an item never reaches the block; sneaking with both hands empty does). 1.20.1 calls `state.use(level, player, hand, hit)`. 1.21.1 calls `state.useItemOn(player.getItemInHand(hand), level, player, hand, hit)` **also when that hand is empty**, and calls `state.useWithoutItem(...)` only if the result is `PASS_TO_DEFAULT_BLOCK_INTERACTION` and `hand == MAIN_HAND`. If nothing consumed, the item's `useOn` follows, then the other hand. So overriding only `useItemOn` on 1.21.1 reproduces the per-hand contract of 1.20.1 `use` exactly (map `PASS` to `PASS_TO_DEFAULT_BLOCK_INTERACTION`).
- Loader patches keep that order [javap F120, N121 `ServerPlayerGameMode.useItemOn`]: Forge fires `ForgeHooks.onRightClickBlock` (cancellable) and adds `ItemStack.doesSneakBypassUse`, then `BlockState.use` (offset 259); NeoForge fires `CommonHooks.onRightClickBlock`, then `BlockState.useItemOn` (265) and `useWithoutItem` (317).
- Trap: client and server evaluate independently; if the client returns `PASS` for the main hand where the server acts, the client then sends the off-hand click too. The mod's precedent is `FrameInteractions.action` (main hand only) with `clientResult` returning `SUCCESS` exactly where the server will act [code `frame/FrameInteractions.java:110-131`].

### 1.2 `onRemove`, state changes, comparators
- `LevelChunk.setBlockState(BlockPos, BlockState, boolean)` [javap four, offsets 313-328]: on the server it calls `oldState.onRemove(level, pos, newState, moved)` for **every** state change at the position, with no same-block test: a property change (`lit` false→true) calls `onRemove` too. If the new state has a block entity the existing instance is kept, `blockEntity.setBlockState(newState)` and `updateBlockEntityTicker` are called (1.21.1 first removes it if `!isValidBlockState(newState)`).
- Default `BlockBehaviour.onRemove` [javap four]: V120, V121, N121 `if (state.hasBlockEntity() && !state.is(newState.getBlock())) level.removeBlockEntity(pos)`; F120 removes also when `!newState.hasBlockEntity()`. An override must do its work inside `if (!state.is(newState.getBlock()))` and **before** `super.onRemove(...)`.
- `BlockEntity.setChanged()` is identical on both [javap V120, V121]: `if (level != null)` → `level.blockEntityChanged(pos)` (chunk marked unsaved) and, unless air, `level.updateNeighbourForOutputSignal(pos, block)` (comparators). It sends nothing to clients.

### 1.4 Item stacks inside a block entity, and the mod's existing seam
- 1.20.1 [javap V120]: `public CompoundTag ItemStack.save(CompoundTag)` (writes `id`, `Count`, `tag`); `public static ItemStack ItemStack.of(CompoundTag)` (returns `EMPTY` on failure, DEBUG log). `ContainerHelper.saveAllItems(CompoundTag, NonNullList<ItemStack>)`, `loadAllItems(CompoundTag, NonNullList<ItemStack>)`.
- 1.21.1 [javap V121]: `public Tag save(HolderLookup.Provider)` and `save(HolderLookup.Provider, Tag)` both throw `IllegalStateException("Cannot encode empty ItemStack")` for an empty stack; `public Tag saveOptional(HolderLookup.Provider)` (empty `CompoundTag` for an empty stack); `public static Optional<ItemStack> parse(HolderLookup.Provider, Tag)`; `public static ItemStack parseOptional(HolderLookup.Provider, CompoundTag)`. `ContainerHelper.saveAllItems/loadAllItems` take a trailing `HolderLookup.Provider`.
- The mod's seam [code `compat/impl/StackTags.java:54-170`]: package-private `final class StackTags`, `static CompoundTag write(HolderLookup.Provider registries, EquipmentSlot slot, ItemStack stack)` → `{slot, data_version, item}` and `static Optional<StowedStack> read(HolderLookup.Provider, CompoundTag[, UUID frameId])`, with the vanilla fixer `DataFixers.getDataFixer().update(References.ITEM_STACK, …, version, current)` for older entries. It is bound to an `EquipmentSlot` (`read` fails with "missing slot"), requires a non-null provider on both versions (`Objects.requireNonNull`, :87) although 1.20.1 does not use it, words its warning for frames, and is reachable only inside `compat/impl` (public face: `FrameStateAccess.stow/takeStowed`). A base class in `compat/impl` could call it, but only after splitting off a slot-less pair and solving the missing provider in 1.20.1 `load`.
- Why a stack in block-entity NBT needs that seam: vanilla's chunk schema types `block_entities` as `DSL.list(DSL.or(References.BLOCK_ENTITY.in(schema), DSL.remainder()))` [javap V121 `net.minecraft.util.datafix.schemas.V2842`]: a block entity id the schema does not know falls into `remainder()` and passes through a 1.20.1→1.21.1 upgrade untouched — primitives survive, a nested stack stays in the 1.20.1 layout (`Count`, `tag`), exactly the `stowed` case. What 1.21.1 then parses from it [not checked]; the cell's charge sits under `tag.exoframes.energy` on 1.20.1 and under `components` on 1.21.1 [code `docs/compat.md:29`].
- The frame registry does not store the cell as a stack: `FrameInteractions.insertCell` turns the held stack into an `EnergyCell` with `CellItem.toCell(ItemStack)` and gives it back with `CellItem.fromCell(EnergyCell)`; the stack carries only `energy` [code `frame/FrameInteractions.java:189-204`, `content/CellItem.java:11-39`]. **The charger can do the same and keep only primitives in NBT (cell present + energy, fuel in RE): no stack seam, no provider, upgrade-safe by construction.**

## 4. Hoppers

A block entity that implements vanilla `WorldlyContainer` is filled and emptied by hoppers on all four variants with **no loader-specific code**.
- `Container` and `WorldlyContainer` have the same abstract methods on both [javap V120, V121; N121 identical, F120 adds one static]: `int getContainerSize()`, `boolean isEmpty()`, `ItemStack getItem(int)`, `ItemStack removeItem(int, int)`, `ItemStack removeItemNoUpdate(int)`, `void setItem(int, ItemStack)`, `void setChanged()` (inherited from `BlockEntity`), `boolean stillValid(Player)`, `void clearContent()`; `int[] getSlotsForFace(Direction)`, `boolean canPlaceItemThroughFace(int, ItemStack, Direction)`, `boolean canTakeItemThroughFace(int, ItemStack, Direction)`. Defaults used by hoppers: `canPlaceItem(int, ItemStack)`, `canTakeItem(Container, int, ItemStack)`, `getMaxStackSize()`; `Container.stillValidBlockEntity(BlockEntity, Player)` on both.
- Vanilla, both versions [javap V120 `getContainerAt(Level, double, double, double)`, V121 `getBlockContainer(Level, BlockPos, BlockState)`]: block `instanceof WorldlyContainerHolder` → its container; else `state.hasBlockEntity()` and `level.getBlockEntity(pos) instanceof Container` → that container. Insert: `canPlaceItem(slot, stack)` and `canPlaceItemThroughFace(slot, stack, side)`, then `setItem(slot, stack)` if the slot is empty, or an in-place `grow` on the stack `getItem` returned, then `setChanged()`. Extract: `getItem(slot)` not empty, `canTakeItem(hopper, slot, stack)` and `canTakeItemThroughFace(slot, stack, side)`, then `removeItem(slot, 1)`; if the hopper cannot take it, the stack is put back with `setItem`. One item per transfer.
- Forge 1.20.1 [javap F120 `HopperBlockEntity.ejectItems` offset 1, `suckInItems` offset 2; src `net/minecraftforge/items/VanillaInventoryCodeHooks.java:35-68, 104-137, 233-252`]: the hopper first calls `VanillaInventoryCodeHooks.insertHook(hopper)` / `extractHook(level, hopper)`, which ask the neighbour block entity for `ForgeCapabilities.ITEM_HANDLER`; without it they return `false` / `null` and the **vanilla `Container` code runs**. `CapabilityProvider.getCapability` is `LazyOptional.empty()` unless something attached a capability (`CapabilityProvider.java:180-183`); Forge has no generic fallback for `Container` block entities (the only `WorldlyContainer` reference in `net.minecraftforge.*` is `SidedInvWrapper`) [src].
- NeoForge 1.21.1 [javap N121 `ejectItems` offset 1, `suckInItems` offset 32; src `net/neoforged/neoforge/items/VanillaInventoryCodeHooks.java:40-68, 98-125, 217-240`]: same shape with `level.getCapability(Capabilities.ItemHandler.BLOCK, pos, state, blockEntity, side)`; `null` → `Optional.empty()` → the vanilla `Container` code runs. `CapabilityHooks.registerVanillaProviders` (`CapabilityHooks.java:60-132`) registers providers for the vanilla block entity types by name; `registerFallbackVanillaProviders` (`:134-158`) covers **only** entity types, bucket items and the milk bucket: there is **no** fallback for block entities that implement `Container`/`WorldlyContainer`, and `BlockCapability.getCapability` consults only providers registered for `state.getBlock()` [src].
- Fabric, both versions [fabric-src `fabric-transfer-api-v1` 3.3.6 and 5.4.5, `HopperBlockEntityMixin`]: its two injections start with "Let vanilla handle the transfer if it found an inventory" (`if (targetInventory != null) return;`, `if (inputInventory != null) return;`); vanilla finds the `Container`. `ItemStorage.SIDED` also has an "Inventory fallback" wrapping any block entity that is a `Container`, so Fabric pipes see the charger for free.
- Needed per variant for hoppers: nothing. Needed only for other mods' pipes: Forge `getCapability` override (`SidedInvWrapper.create(WorldlyContainer, Direction...)`), NeoForge `RegisterCapabilitiesEvent.registerBlockEntity(Capabilities.ItemHandler.BLOCK, type, SidedInvWrapper::new)` — loader-specific, outside the design's "hopper compatible".
- Traps: (a) hoppers mutate the stack returned by `getItem` when merging, so a slot that can hold more than one item must return a live stack; a one-item cell slot can return a fresh view. (b) `setItem` receives the hopper's own one-item stack: normalise it (cell → `EnergyCell`). (c) The contents must drop on break (§5). (d) `GameTestHelper.assertContainerEmpty/assertContainerContains` only understand `BaseContainerBlockEntity` (§7).

## 5. Dropping contents; marking changed; notifying clients

- `Containers` [javap V120, V121; F120 = V120, N121 = V121]: on both `static void dropContents(Level, BlockPos, Container)`, `dropContents(Level, Entity, Container)`, `dropContents(Level, BlockPos, NonNullList<ItemStack>)`, `dropItemStack(Level, double, double, double, ItemStack)`; 1.21.1 only: `dropContentsOnDestroy(BlockState, BlockState, Level, BlockPos)` (same-block guard + `dropContents` for a `Container` block entity + `updateNeighbourForOutputSignal`).
- Version-neutral `onRemove` (see 1.2 for why the guard is mandatory and why it precedes `super`):
```java
@Override
public void onRemove(BlockState state, Level level, BlockPos pos, BlockState newState, boolean moved) {
    if (!state.is(newState.getBlock()) && level.getBlockEntity(pos) instanceof ChargerBlockEntity charger) {
        Containers.dropContents(level, pos, charger);          // or dropItemStack(level, x, y, z, stack)
        level.updateNeighbourForOutputSignal(pos, this);
    }
    super.onRemove(state, level, pos, newState, moved);
}
```
  `onRemove` runs on the server only, also for creative break, explosions and `/setblock`. The fuel already converted to RE is not an item: lost on break unless the plan refunds whole dust.
- Data changed (energy, fuel): `setChanged()` — saves and updates comparators, on both (1.2). Call it only when a value really changed.
- Visible state changed: `level.setBlock(pos, state.setValue(PROPERTY, value), Block.UPDATE_ALL)` (`UPDATE_NEIGHBORS = 1`, `UPDATE_CLIENTS = 2`, `UPDATE_ALL = 3` on both [javap]). Clients receive the new blockstate through the normal block update; the block entity instance survives (1.2); light is recomputed when `lightLevel` differs between the two states. Do it only when the derived value differs from `getBlockState()`, as furnaces do, never every tick.
- If block-entity data itself had to reach clients: `getUpdateTag` + `getUpdatePacket` (§2) and `level.sendBlockUpdated(pos, state, state, Block.UPDATE_CLIENTS)` (`Level.sendBlockUpdated(BlockPos, BlockState, BlockState, int)` on both). Not needed with blockstate properties.

## 8. What this changes for the plan of part 3c

**Statements of `stato-del-codice.md` on this topic.** Confirmed: §5 and §10 "no block, block item, block entity, block entity type, blockstate/model, loot table, tag, `block.` lang key"; §5 the `CompatEntity`/`EntityBase` pattern; §10 the `load`/`loadAdditional`, `saveAdditional`, `getUpdateTag` and `use`/`useItemOn`/`useWithoutItem` signatures and "`BlockEntityType.Builder.of(...)`/`build(Type)` identical"; §7.1 data folder names and recipe result format; §2.1 `energy.chargerRePerRedstone = 500` present, no charge rate or fuel capacity [code `core/config/ExoframesConfig.java:39`]; §7.2 rules of `check_sources.sh`; §7.5 the `add(tests,` count (95). **Corrected:** §7.5 "a new block entity type on Fabric will very likely add a `No data fixer registered for <id>` WARN" is wrong on all four variants (1.5): no log line, no `tools/log_allowlist.txt` entry. **Added:** §10 "`BaseEntityBlock` on 1.21.1 has an abstract `codec()`" is true but avoidable (`extends Block implements EntityBlock`); the hooks' visibility changed (`public` → `protected`); `BlockEntitySupplier` is accessible on Fabric only through Fabric API's transitive access widener.

**Recommendations.**
1. Two seams, each with one job: `compat/impl/EntityBlockBase` (the click) and `compat/impl/BlockEntityBase` (load/save), with the directive-free `compat/CompatEntityBlock` and `compat/CompatBlockEntity` in front (§2). Update `docs/compat.md` (rows :205-206 and a "Fuori dalle interfacce" paragraph each). No `Compat` accessor, no `platform/` change, no mixin, nothing for `check_jars.sh`.
2. `ChargerBlock extends CompatEntityBlock` and `ChargerBlockEntity extends CompatBlockEntity implements WorldlyContainer`, without directives, in `content/` or the `block/` package `docs/compat.md:3` already announces. Do not extend `BaseEntityBlock` or `HorizontalDirectionalBlock`.
3. Persist primitives only: cell present + its energy, fuel in RE (reuse `NbtKeys.CELL`, `NbtKeys.ENERGY`; add a fuel key to `NbtKeys`). Keep the cell in memory as an `EnergyCell` (as `FrameState` does) and build the stack with `CellItem.fromCell` when it leaves. This avoids the stack seam, the provider, per-tick component writes and the upgrade problem of 1.4. Consequence to state in the design: a cell loses any extra stack data (custom name) in the charger, exactly as in a frame today.
4. Put the charging rule (fuel → cell per tick, RE per dust, capacities) in `core/energy` as a pure class with JUnit tests (`check_sources.sh` rule 1c), and add the missing config fields (charge rate, fuel capacity) with `ConfigValidation` and `ExoframesConfigTest`.
5. Hoppers are cheap: about a dozen neutral methods on the block entity and no loader code (§4). Suggested shape: slot 0 = cell (one item; in from top and sides, out from the bottom only when the plan says so, e.g. when full), slot 1 = fuel inlet that accepts redstone dust only while the buffer has room and converts it on `setItem` (always reads empty, `getMaxStackSize()` 1) — or a real dust slot if the plan prefers furnace-like behaviour (then that slot must return a live stack and its dust drops on break).
6. Show state through blockstate properties (`BlockStateProperties.LIT` for charging, optionally a custom `BooleanProperty` for "cell inside", optionally `HORIZONTAL_FACING`), changed with `level.setBlock(..., Block.UPDATE_ALL)` only on change; no block-entity sync, no client code (§5, §6). The same properties let the client-side branch of `onUse` answer like the server (1.1 trap).
7. Interaction like `FrameInteractions`: main hand only; client returns `SUCCESS` where the server will act and `PASS` otherwise; server acts and returns `SUCCESS`/`CONSUME`; give the cell back with `Handouts.give(ServerPlayer, ItemStack)` [code `frame/Handouts.java:34`]; consume the held item unless `instabuild`. No gesture that needs sneaking with an item in hand (it never reaches the block).
8. `onRemove` with the same-block guard, drop, then `super` (§5); decide whether leftover fuel is refunded as dust.
9. `RedstoneExoframes.init()`: `ModBlocks.register()` before `ModItems.register()`, then `ModBlockEntities.register()` (§3); build the `BlockEntityType` only inside its supplier.
10. Resources: assets in the common tree; loot table, `mineable/pickaxe` tag and recipe in the two per-version trees from `tools/gen_data.py`; `block.redstone_exoframes.charger` in both lang files; textures added to `tools/gen_placeholders.py` `outputs()` if generated.
11. Tests: direct-tick GameTests for the rule on the real block entity; one real-time test proving the ticker is wired (`getTicker`); one click test through `player.gameMode.useItemOn` per gesture; one hopper-in and one hopper-out test; one save/load round trip through the two test-only helpers of §2; one "break drops the cell" test that removes the item entity.

**Open points (not settled here).**
- How each loader's client applies a block-entity update packet (`load` vs `loadWithComponents`, Forge `onDataPacket`/`handleUpdateTag`, NeoForge `handleUpdateTag`) [not checked] — irrelevant if recommendation 6 is taken.
- What 1.21.1 parses from a stack tag left in the 1.20.1 layout inside an unknown block entity [not checked] — irrelevant if recommendation 3 is taken.
- Nothing here was compiled or run: the two bases and the Fabric ordering of §3 are derived from bytecode and sources. The first task of the charger should be the two bases plus an empty block registered on all four variants, with the GameTests on four variants as the proof.
- Rendering of the block and its item in the real client (models, light) is for the headless client run.
- Design decisions left to the plan: facing or not; which faces accept and release what; whether a hopper may take a cell before it is full; one dust per click or as many as fit; what a click with a cell does when a cell is already inside; comparator output; refund of fuel on break; the two new config values.
