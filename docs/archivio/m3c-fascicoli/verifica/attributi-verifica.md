## Missed (by the dossier, relevant to the plan)

1. **Knockback resistance is not only `LivingEntity.knockback`** (see C4): arrows (`AbstractArrow`, Punch/knockback), the Warden's sonic boom and, on 1.21.1, the mace read the target's `KNOCKBACK_RESISTANCE` directly; explosions read it on neither version (1.20.1 blast-protection dampener, 1.21.1 the separate `EXPLOSION_KNOCKBACK_RESISTANCE`). If the design promises "the suit is not pushed by explosions", a modifier on `KNOCKBACK_RESISTANCE` does not deliver it; on 1.21.1 a second modifier on `EXPLOSION_KNOCKBACK_RESISTANCE` would (syncable, [0, 1]); 1.20.1 has no attribute for it.
2. **The pilot's own fall-damage sound is produced on the client, not by the server.** [javap V120/V121] `Entity.checkFallDamage` → `Block.fallOn` → `Entity.causeFallDamage` runs for the `LocalPlayer` too; `LivingEntity.causeFallDamage` plays the sound before `hurt`, and `LocalPlayer.hurt` is `return false`. On the server, `Player.playSound` excludes the player itself (C10). So: cancelling `LIVING_HURT` on the server cannot silence anything for the pilot; the 1.21.1 `FALL_DAMAGE_MULTIPLIER` route works for the pilot only because the attribute is synced and the client computes 0 too; on 1.20.1 any change to what the pilot hears needs client-side code. Forge/NeoForge also post `LivingFallEvent` on both sides (`ForgeHooks.onLivingFall` / `CommonHooks.onLivingFall` at the top of `causeFallDamage`).
3. **`level.playSound(Player, …)` on the client plays only if that player is `minecraft.player`** [javap V120/V121 `ClientLevel.playSeededSound`: `if (player == minecraft.player) playSound(…)`]. A common-code call with `null` that also runs client-side plays nothing there; the pattern "client predicts with `level.playSound(player, …)`, server broadcasts with the same `player` excluded" gives each listener exactly one sound. The dossier's rule 8 ("`null` from server code") is right for server-only code but does not say this.
4. **NeoForge's `Item.getBarWidth` has no clamp** (C11): a cell whose charge exceeds `cellCapacity` (config lowered between sessions, or a remote client with a smaller value) gives width > 13 unless the override clamps. The dossier says 1.21.1 clamps.
5. **FOV has a loader hook on Forge/NeoForge only** (C4): F120 `ForgeHooksClient.getFieldOfViewModifier` / N121 `ClientHooks.getFieldOfViewModifier` (the FOV-modifier event) at the end of `getFieldOfViewModifier`; vanilla Fabric has none. If the plan decides to neutralise the speed-modifier FOV narrowing, it needs a mixin on Fabric (both versions) or two different mechanisms; Architectury event availability for FOV [not checked].
6. **Ctrl+B on 1.21.1** additionally requires `GameNarrator.isActive()` (narrator available on the system) besides `narratorHotkey`; on 1.20.1 it is unconditional. Only refines the dossier's caveat for B; the recommendation (avoid B) stands.
7. **`sendDirtyEntityData` for a ridden/riding player** runs in the passenger branch too (V120 offset 384, V121 387): the sync delay is still `updateInterval` 2, but for a player that is a passenger the path differs; no change to conclusions, noted because the dossier names only one call site.
