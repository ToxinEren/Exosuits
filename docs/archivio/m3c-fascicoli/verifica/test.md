### 1.2 Who ticks it
**The level does** [javap, the four]. `ServerLevel.addNewPlayer` → `addPlayer` → `PersistentEntitySectionManager.addNewEntity` (Fo20/Neo21 `addNewEntityWithoutEvent`, after posting `EntityJoinLevelEvent`) → `addEntity[WithoutEvent]`: `getEffectiveStatus(entity, …)` returns `Visibility.TICKING` when `isAlwaysTicking()` (`Player.isAlwaysTicking()` = `true`) → `startTicking` → `LevelCallback.onTickingStart` → `ServerLevel$EntityCallbacks.onTickingStart`: `entityTickList.add(entity)`. `ServerLevel.tick` → `entityTickList.forEach(lambda)` (V20 `@402`, V21 `@447`, Fo20 `@400`, Neo21 `@450`; guarded by `!players.isEmpty() || forced chunks || emptyTime++ < 300`); the lambda: not removed, `shouldDiscardEntity` false, [1.21.1 `!tickRateManager.isEntityFrozen`], `checkDespawn()`, `distanceManager.inEntityTickingRange(entity.chunkPosition().toLong())`, no vehicle → `guardEntityTick(this::tickNonPassenger, entity)`. `ServerLevel.tickNonPassenger(Entity)`: `entity.setOldPosAndRot()@1`, `++entity.tickCount@11-16`, `entity.tick()` (V20/V21 `@44`, Fo20 `@51`, Neo21 `@54` between `EventHooks.fireEntityTickPre` — cancelable — and `fireEntityTickPost`).
- The only condition that can fail is `inEntityTickingRange`. - [log] corroboration: mocks earn "Suit Up" (`inventory_changed` with iron armor) 12 / 12 / 9 / 12 times on 1.20.1-fabric / 1.20.1-forge / 1.21.1-fabric / 1.21.1-neoforge (e.g. `versions/1.20.1-fabric/build/gametest/server.log:464-475`). **The connection does not** [javap + code]. `doTick()` is called only by `ServerGamePacketListenerImpl.tick()` (`@78`, both versions), which is called by `Connection.tick()` (`TickablePacketListener`), which `ServerConnectionListener.tick()` calls for the entries of its own `connections` list (V20 `@1-54`). The mock's `Connection` is built by hand and never added to that list [code `GameTestsImpl.java:102-103`]. `PlayerList.tick()` only broadcasts latency every 600 ticks [javap, the four].

**Order inside one server tick** [javap `MinecraftServer.tickChildren`]: every `ServerLevel.tick` (V20 `@125`, V21 `@142`, Fo20 `@133`, Neo21 `@150`) → `ServerConnectionListener.tick()` (`@197` / `@214` / `@251` / `@268`) → `PlayerList.tick()` (`@216` / `@233` / `@270` / `@287`) → `GameTestTicker.SINGLETON.tick()` (V20 `@228` and V21 `@255` behind `SharedConstants.IS_RUNNING_IN_IDE`; Fo20 `@282` behind `ForgeGameTestHooks.isGametestEnabled()`; Neo21 `@309` behind `GameTestHooks.isGametestEnabled() && tickRateManager.runsNormally()`; Fabric: `fabric-gametest-api-v1` 1.2.15 and 2.0.5 `MinecraftServerMixin` injects after the `PlayerList.tick()` call when `!IS_RUNNING_IN_IDE` [sources jar]). A test tick is `level.getGameTime() - startTick` and `runAfterDelay(n, r)` = `runAtTickTime(getTick() + n, r)` [javap `GameTestInfo.tickInternal`, `GameTestHelper`, both versions]. **So a test body and every later callback run after the level tick of their server tick, and between a body and a callback n ticks later the level has run `ServerPlayer.tick()` on the mock exactly n times.**

### 1.6 Recipes (all without reflection; `tick()`, `hurt`, `causeFallDamage`, `doCheckFallDamage`, `jumpFromGround` are public, `Entity.invulnerableTime`, `tickCount`, `fallDistance` are public fields [javap])
**(d) End the spawn protection.** `for (int i = 0; i < 60; i++) player.tick();` right after creating the mock. Harmless: the body is the list of §1.3, the same call the level makes once per tick; it fires no Architectury event, moves nothing, leaves `tickCount` alone. Side effects to know: it also decrements `invulnerableTime` (so call it before the first hit, never between two hits of an i-frame test) and closes a container that is no longer valid. The alternative, waiting 60 level ticks with `runAfterDelay(60, …)`, is exact by §1.2 but leaves 20-40 ticks of the 100 and depends on the mock standing in an entity-ticking chunk for those 60 ticks.
**(a) One hit of a known amount through the whole vanilla path.**
```java
ServerPlayer p = Compat.gameTests().mockServerPlayer(helper);
p.setGameMode(GameType.SURVIVAL);                    // abilities.invulnerable = false
for (int i = 0; i < 60; i++) p.tick();               // spawnInvulnerableTime 60 -> 0
float before = p.getHealth();
boolean hit = p.hurt(helper.getLevel().damageSources().cactus(), 8.0F);
```
`cactus` [data, both versions]: not in `bypasses_armor`, `bypasses_invulnerability`, `is_fire`, `is_fall`; `"scaling": "when_caused_by_living_non_player"` and no causing entity, so `DamageSource.scalesWithDifficulty()` is false [javap, the four] and the amount at the event is the same on the three loaders. `DamageSources.cactus()` exists with that signature on the four. Vanilla then: `hit == true`; `p.invulnerableTime == 20`; `Player.actuallyHurt` → `getDamageAfterArmorAbsorb` → `Player.hurtArmor(source, 8.0F)` (the wear point; the placeholders are not damageable, `danno.md` §6) → `CombatRules.getDamageAfterAbsorb`: `damage * (1 - clamp(armor - damage / (2 + toughness / 4), armor * 0.2, 20) / 25)` with `armor = getArmorValue() = Mth.floor(ARMOR attribute)` [javap, same constants on both versions]. With armor 15 and toughness 0: 8 → 4.48, health 15.52; with armor 0: health 12. Do not use `generic()` (bypasses armor), `mobAttack` (scales with difficulty), `playerAttack` (PvP off), nor amounts near 20 (death runs `FrameEntry.onDeath`).
**(b) Two hits inside the i-frame window.** `LivingEntity.hurt` (V20 `@194-276`, V21 `@229-303`, Fo20 `@249-311`, Neo21 `@363-476`): `if ((float) invulnerableTime > 10.0F && !source.is(BYPASSES_COOLDOWN)) { if (amount <= lastHurt) return false; actuallyHurt(source, amount - lastHurt); lastHurt = amount; } else { lastHurt = amount; invulnerableTime = 20; actuallyHurt(source, amount); }` (Neo21: 20 comes from `DamageContainer.getPostAttackInvulnerabilityTicks()`, default 20). `bypasses_cooldown` has no file in either version [data]: every source obeys the gate. For a `ServerPlayer` only `ServerPlayer.tick` decrements `invulnerableTime` (`LivingEntity.baseTick` skips `instanceof ServerPlayer`: V20 `@609-629`, V21 `@628-648`, Fo20 `@333-353`, Neo21 `@359-379`). So: a second `hurt` in the same tick, or in a callback up to 9 ticks later, is inside the window — `p.hurt(cactus, 5.0F)` returns false and health does not move; `p.hurt(cactus, 10.0F)` returns true and removes the after-armor value of 2.0 (0.88 with armor 15). From 10 ticks on (or after `p.invulnerableTime = 0;`) the hit is full again. The mod's `LIVING_HURT` listener is called for all of them on the three loaders (it is before the gate); a mixin at `Player.hurtArmor` is called only for what passes (`danno.md` §2). `lastHurt` is `protected`; `invulnerableTime` is the only part of the gate a listener can read.
**(c) Fall damage.** `p.causeFallDamage(10.0F, 1.0F, p.damageSources().fall())` — `Player.causeFallDamage(float, float, DamageSource)`: returns false at once if `abilities.mayfly` (creative); `FALL_ONE_CM` stat; `LivingEntity.causeFallDamage` → `calculateFallDamage` (V20 `ceil((d - 3 - jumpBoost) * m)`, V21 `ceil((d - SAFE_FALL_DISTANCE) * m * FALL_DAMAGE_MULTIPLIER)`) = 7 → sounds → `hurt(fall, 7.0F)` → the gates of §1.4-1.5 → `fall` bypasses armor → health −7.0. It **returns true even when `hurt` refused or the mod cancelled**: assert on `getHealth()`. The path a landing packet takes is also callable: `p.fallDistance = 10.0F; p.doCheckFallDamage(0.0, -1.0, 0.0, true);` (`ServerPlayer.doCheckFallDamage(double, double, double, boolean)` → `Entity.checkFallDamage` → `Block.fallOn@13` → `causeFallDamage(fallDistance, 1.0F, fall())`, then `resetFallDistance()`; stand the mock on a plain block, since hay, slime, beds and farmland override `fallOn`, and out of water, which resets `fallDistance` first). A mock cannot be made to fall "for real": `ServerPlayer.checkFallDamage(double, boolean, BlockState, BlockPos)` is an empty override on the four, so the physics of `doTick()` neither accumulates `fallDistance` nor lands.
**Control for (c), mandatory:** the same call on a mock without the frame must lose exactly 7.0. Inside the first 60 ticks, or in creative, "no fall damage" passes with no mod code at all.
**Traps.** `doTick()` between a hit and its assertion can heal (natural regeneration, §1.3) and moves a mock that is in the air. A mock that died stays dead (no respawn). Vanilla refuses hits on `isDeadOrDying()`. The game rule `fallDamage` and the difficulty are shared by all tests of the run: do not change them.

## 2. The jump statistic [javap, the four]
- `ServerGamePacketListenerImpl.handleMovePlayer(ServerboundMovePlayerPacket)`: `boolean flag = d7 > 0.0` where `d7` = clamped packet Y − `lastGoodY`; `if (player.onGround() && !packet.isOnGround() && flag) player.jumpFromGround();` — V20 `@704-744`, V21 `@644-684`, Fo20 `@708-748`, Neo21 `@645-685`. Reached only when the player is not a passenger (early return V20 `@241-299`), not sleeping, has no pending teleport confirmation (`awaitingPositionFromClient == null`) and did not move too quickly. After it: `player.move(MoverType.PLAYER, delta)`, `absMoveTo`, `doCheckFallDamage`, `setOnGroundWithKnownMovement(packet.isOnGround(), …)`, `if (flag) resetFallDistance()`, `checkMovementStatistics` (V20 `@776-1328`).
- `Player.jumpFromGround()` (public in `Player` on the four; `ServerPlayer` does not override it): `super.jumpFromGround()` (`LivingEntity`: sets the server-side `deltaMovement` to the jump power, plus 0.2 along the yaw when sprinting; Fo20 `ForgeHooks.onLivingJump@75`, Neo21 `CommonHooks.onLivingJump@85`), `awardStat(Stats.JUMP)` (`@5-8`, unconditional), `causeFoodExhaustion(isSprinting() ? 0.2F : 0.05F)`. It is the only reference to `Stats.JUMP` in the classes read (`Entity`, `LivingEntity`, `Player`, `ServerPlayer`, the packet listener); on the server `LivingEntity.aiStep` does not reach it for a player on foot (the server has no jump input; `jumping` is set only by `setPlayerInput` while riding).
- **The exact condition is "left the ground upwards between two position packets"**, whatever the cause. Counted: a jump, an auto-jump, any game mode (creative too), the jump that starts a creative flight, swimming up from the bottom of water (the client calls `jumpInLiquid`, the server still sees ground → air with dy > 0), being lifted off the ground by knockback, an explosion, a slime block, a bubble column, starting to climb a ladder from the floor [deduced from the condition, not observed]. Not counted: anything while already off the ground (creative flight, swimming, mid-water), stepping up (the packet stays `onGround`), anything as a passenger, packets without position.
- Reading: `player.getStats().getValue(Stats.CUSTOM.get(Stats.JUMP))` — `ServerPlayer.getStats()` returns `ServerStatsCounter`; `StatsCounter.getValue(Stat<?>)` and `<T> getValue(StatType<T>, T)`; `Stats.CUSTOM` is `StatType<ResourceLocation>`, `Stats.JUMP` a `ResourceLocation`; identical on the four. `StatsCounter.increment` saturates at `Integer.MAX_VALUE`; `ServerPlayer.resetStat(Stat<?>)` exists: a reader must treat a decrease as a new baseline.
- **A mock has a working counter**: `ServerPlayer.<init>` takes it from `PlayerList.getPlayerStats(Player)` (map by UUID, file `stats/<uuid>.json` under the world; a fresh random UUID per mock, so it starts at 0). In a test: `p.jumpFromGround();` (the very call the packet handler makes) or `p.awardStat(Stats.JUMP);` (`Player.awardStat(ResourceLocation)` → `ServerPlayer.awardStat(Stat<?>, int)` → `stats.increment`). Driving `handleMovePlayer` itself on a mock is possible in principle (`p.connection` is real and `PacketUtils.ensureRunningOnSameThread` runs inline on the server thread) but the handler returns early until the teleport sent by `placeNewPlayer` is confirmed with its private id: not worth it.

## 3. A real remote player at `TickEvent.PLAYER_PRE` / `PLAYER_POST` [javap]
`ServerGamePacketListenerImpl.tick()`, both versions, loaders unpatched in this part: `resetPosition()` `@29` (`firstGood* = lastGood* =` current position); `player.xo/yo/zo = player.getX/Y/Z()` `@33-71`; `player.doTick()` `@78`; **`player.absMoveTo(firstGoodX, firstGoodY, firstGoodZ, yRot, xRot)` `@82-111`**. `Entity.isControlledByLocalInstance()` → `isEffectiveAi()` → `!level.isClientSide`, with no override in `Player` or `ServerPlayer`: the server does run `LivingEntity.travel` physics for a player inside `doTick()` and then throws the displacement away. The position changes only in `handleMovePlayer` (`absMoveTo` to the client's position, which also sets `xo/yo/zo`) and in teleports. Move packets are handled as server tasks between ticks [handler entry `PacketUtils.ensureRunningOnSameThread` read; that none runs inside `tickChildren` not checked].

| At `PLAYER_POST` (end of `Player.tick`) | What it holds | Use |
|---|---|---|
| `getX/Y/Z()` | last position accepted from the client **plus this tick's server-side physics step** (gravity when airborne; horizontal only if the server-side velocity is not zero: knockback, the 0.2 sprint-jump boost of the server-side `jumpFromGround`); reverted right after | sample it at `PLAYER_PRE` instead: there it is exactly the accepted client position |
| `xo/yo/zo` | position at the start of this connection tick | `getX() - xo` = the phantom step only |
| `xOld/yOld/zOld` | position at this tick's level tick (`setOldPosAndRot`), i.e. the same accepted position | no |
| `getDeltaMovement()` | the server's own velocity (the server has no input: `xxa = zza = 0`) | no |
| `walkDist` | grows by 0.6 × horizontal length of every `Entity.move` (V20 `@660-672`): packet moves and phantom steps; not as a passenger, in creative flight, or sneaking on the ground (`Player.getMovementEmission`). `walkDistO` is set in this tick's `baseTick@63` | only through an own previous value; a `float` |
| `isSprinting()` | shared flag 3. **Horizontal distance since the previous server tick:** nothing vanilla holds it at tick time. Keep the previous `position()` per player (a map emptied at `PLAYER_QUIT`, like the `EnergyMeter` map), sampled at the same point each tick — `PLAYER_PRE` gives the clean value — and take `hypot(dx, dz)`; reset the sample (count 0) when the level changed, when the step is implausible (a teleport), and treat a passenger as not moving by its own means. Per-tick values are jittery (0, 1 or 2 client packets land in one server tick), so classify over a short window (for instance the sum of the last 5-10 ticks), not on one tick. Vanilla's own classification exists as statistics — `checkMovementStatistics(dx, dy, dz)` (in `Player` on 1.20.1, in `ServerPlayer` on 1.21.1; called from `handleMovePlayer` and from `travel`): on the ground `SPRINT_ONE_CM` if `isSprinting()`, else `CROUCH_ONE_CM` if `isCrouching()`, else `WALK_ONE_CM`; airborne distance goes to `FLY_ONE_CM` only above 25 cm per call; water has its own three — usable but coarser than a position sample, and sprint-jumping lands mostly in `FLY_ONE_CM`.
**Is sprinting:** `player.isSprinting()`. Walking about 0.21 and sprinting about 0.28 blocks per tick (recon-mov measured 8.5 and 11.0 blocks in 2 s) are too close to tell apart from jittery distances; the flag is what the client itself decided. Activity = not moved → IDLE; moved and `isSprinting()` → SPRINT; else WALK.
**On a mock** all of this is under the test's control: `p.setPos(x + 0.2, y, z)` between two direct calls of the mod's tick method is a walked tick, `p.setSprinting(true)` the flag; nothing else moves a mock (no `doTick`).

- **Client sprint logic, `LocalPlayer.aiStep`.** `canStartSprinting()` = `!isSprinting() && hasEnoughImpulseToStartSprinting() && hasEnoughFoodToStartSprinting() && !isUsingItem() && !hasEffect(BLINDNESS) && (!isPassenger() || vehicleCanSprint(getVehicle())) && !isFallFlying()`. `hasEnoughFoodToStartSprinting()` = `isPassenger() || foodLevel > 6.0F || abilities.mayfly` (Neo21: `mayFly()`). `hasEnoughImpulseToStartSprinting()` = `isUnderWater() ? input.hasForwardImpulse() : input.forwardImpulse >= 0.8`. V20: `canStartSprinting()` stored once (`@381`); `setSprinting(true)` at `@471` (double-tap, or key) and `@520` (sprint key, `!isInWater() || isUnderWater()`), both only if it was true; while sprinting, `!input.hasForwardImpulse() || !hasEnoughFoodToStartSprinting()` (`@531-552`), a non-minor horizontal collision, or `isInWater() && !isUnderWater()` → `setSprinting(false)` (`@632`, `@645`). Fo20 and Neo21 restructure the same block (`canStartSprinting@389` / `@415`, `setSprinting(true)@495, @586` / `@521, @612`) and replace the water tests with `canStartSwimming()` and `isInFluidType(…)`: injecting into `aiStep` by ordinal differs per loader; the two private predicates do not. `hasEnoughFoodToStartSprinting` is the one method that decides both the start and the stop.
- **Sending.** `sendIsSprintingIfNeeded()`: `if (isSprinting() != wasSprinting) { send ServerboundPlayerCommandPacket(START_SPRINTING | STOP_SPRINTING); wasSprinting = isSprinting(); }`. The latch `wasSprinting` is client-only.
- **Server.** `handlePlayerCommand`: `START_SPRINTING` → `player.setSprinting(true)`, `STOP_SPRINTING` → `player.setSprinting(false)`, nothing else. `LivingEntity.setSprinting(boolean)`: shared flag 3, then removes the `SPEED_MODIFIER_SPRINTING` modifier of `MOVEMENT_SPEED` and re-adds it (transient) when true.
- **Does a server-side `player.setSprinting(false)` reach the client? Yes, both parts.** `ServerEntity.sendDirtyEntityData()` (private, the four): dirty synced data → `ClientboundSetEntityDataPacket` (the whole shared-flags byte) through `broadcastAndSend`, which also sends to the entity's own connection when it is a `ServerPlayer` (`@11-31`); then dirty attributes (V20 `getDirtyAttributes()`, V21 `getAttributesToSync()`) → `ClientboundUpdateAttributesPacket` the same way. Only if the server's flag was set (`SynchedEntityData.set` ignores an equal value [not re-read]). What the client does next is its own `aiStep`: with the sprint key down it sets the flag again in its next tick, and since `wasSprinting` is still true it sends nothing — the server then believes "not sprinting" while the client sprints. This is the bytecode reason for recon-mov's measurement that the server side alone does not stop the sprint.
- **Swimming.** `Entity.updateSwimming()` (V20 = V21): `if (isSwimming()) setSwimming(isSprinting() && isInWater() && !isPassenger()); else setSwimming(isSprinting() && isUnderWater() && !isPassenger() && level().getFluidState(blockPosition).is(FluidTags.WATER));`. `Player.updateSwimming()` (the four): `if (abilities.flying) setSwimming(false); else super.updateSwimming();`. **Do transient attribute modifiers survive?** On the same object, yes (nothing touches the `AttributeMap`). On a new object, no, on both versions: V20/Fo20 `restoreFrom` copies no attribute at all; V21 `restoreFrom@42-49` (same statement in Neo21) calls `AttributeMap.assignBaseValues(old)`, whose lambda copies only `getBaseValue()` → `setBaseValue` (`method_60613`); modifiers of any kind are not copied (`assignAllValues` is the client-side one). On 1.21.1 with `keepEverything` the mob effects are re-added (`@92-131`), which rebuilds effect modifiers but not the mod's. Transient modifiers are also not saved (`AttributeInstance.save()` writes `permanentModifiers` only [javap V20, V21]), so a login starts without them.
**When the mod must re-apply its modifiers:** at `PLAYER_JOIN` and at `PLAYER_RESPAWN`, whenever a worn record exists for the player. `PLAYER_RESPAWN` covers both death (then no record: nothing to apply, and the new object carries nothing to clear) and the End return (the record and the placeholders survive `keepEverything`; the new object has no modifiers). Ordinary dimension changes need nothing; an idempotent `apply` there is harmless. `PLAYER_CLONE` is too early to be useful (the new player is not in a level yet) and adds nothing over `PLAYER_RESPAWN`.

## 6. What this changes for the plan of part 3c
1. **First GameTest of the part: a probe of §1.2**, because everything in §1.6 rests on it and it was read, not run: a mock prepared as in recipe (a) and moved into the structure, `int t = p.tickCount`, one `hurt(cactus, 1.0F)`, `runAfterDelay(5, …)` → `p.tickCount == t + 5` and `p.invulnerableTime == 15`. If it fails on a variant, recipe (d) still works (it does not depend on the level) and only the "wait n ticks" arithmetic of (b) changes.
2. **Correct the comment at `ExoframeGameTests.java:136`** (and the reconnaissance sentence): the level advances a mock's `tickCount` and runs `ServerPlayer.tick()`; what never runs is `doTick()` / `Player.tick()`.
3. **Test helpers** (private methods of the test class, no compat seam needed, no version difference): `endSpawnProtection(ServerPlayer)` = 60 × `tick()`; `survivalMock(helper)` = mock + `setGameMode(SURVIVAL)` + `endSpawnProtection`. Damage tests: `damageSources().cactus()`, amounts well under 20, assertions on `getHealth()` and on the mod's state, never on the return value of `causeFallDamage`; i-frame tests: second hit in the same tick, and `p.invulnerableTime = 0` (public) to leave the window; fall tests with the frameless control.
4. **Mod code of 3c must not branch on `player.isCreative()`** for damage, energy or effects: every mock answers `true`, so tests would silently take the creative branch. Use `getAbilities().invulnerable` / `instabuild`, as vanilla does.
5. **The per-player server tick must be a directly callable method** (`tick(ServerPlayer)`), registered on the tick event and called by tests N times ("consumo di energia su N tick"); for a mock no event fires. Avoid `doTick()` in those tests (physics, food, healing). Read the position at `PLAYER_PRE` (the mod already listens there for `SuitSize.tick`): at `PLAYER_POST` the position carries the server's phantom step.
6. **Activity:** own previous-position map + a short window for "moved", `isSprinting()` for the sprint, passengers and teleports excluded (§3). Thresholds and window length are the builder's choice (design §6) and need numbers from a real client [not measured here].
7. **Jumps:** per player, last seen `Stats.JUMP`; first sight and any decrease = baseline; each increment = one `FrameRules.jump`. Say in the design that the count is "left the ground upwards" (knockback, bubble columns, ladders and swim-starts included). With recon-mov's water rule the suit does not jump in water at all, which removes the swim-start case.
8. **Sprint:** the client-side switch is `LocalPlayer.hasEnoughFoodToStartSprinting()Z` (private; Fabric `method_46743`, Forge `m_255269_`), as recon-mov found; the server's `setSprinting(false)` is bookkeeping only and, against a client without the mixin, makes the server's flag wrong rather than the client slower (§4).
9. **Attributes:** re-apply at `PLAYER_JOIN` and `PLAYER_RESPAWN` (two-argument form on 1.20.1, three on 1.21.1; ignore the third: it is `null` on NeoForge). A GameTest of it needs a seam, for instance `GameTests.respawn(ServerPlayer, boolean keepEverything)` → `PlayerList.respawn(p, keep)` on 1.20.1 and `respawn(p, keep, keep ? CHANGED_DIMENSION : KILLED)` on 1.21.1; the returned player is a plain `ServerPlayer` (no `isCreative` override, no recorded messages) born at the world spawn.
