## Missed (what would mislead a planner)
1. Hoppers ignore the container's max stack size. [javap V120/V121 `HopperBlockEntity.tryMoveInItem` offsets 66-99] the merge limit is `stack.getMaxStackSize() - existing.getCount()`, and `isFullContainer` compares `getItem(slot).getCount()` with `ItemStack.getMaxStackSize()` (V121 lambda offsets 31-45). Recommendation 5's "`getMaxStackSize()` 1" on the inlet slot limits nothing: every limit must live in `canPlaceItem`/`canPlaceItemThroughFace` (or in `getItem` reading empty). Cells are `stacksTo(1)`, so the cell slot cannot be merged into.
2. Extraction rollback differs by version. If the hopper cannot accept the item: V120 `tryTakeInItemFromSlot` does `setItem(slot, copyTakenBefore)` (68-72); V121 does `stackFromGetItem.setCount(original)` and calls `setItem` only when the original count was 1 (68-85; NeoForge `ejectItems` uses the same pattern for its own slots). A `getItem` that returns a fresh copy of a multi-item slot loses items on 1.21.1 only. Trap (a) gives a different reason for the same rule; a one-item slot is safe on both.
3. Loader patches change the right-click gate. [javap F120/N121 `ServerPlayerGameMode.useItemOn`] `RightClickBlock` event first (41; cancellable, `getUseBlock()` DENY/FALSE skips the block, 226-240); `ItemStack.onItemUseFirst(UseOnContext)` runs BEFORE the block (128); the sneak skip is `isSecondaryUseActive && anyHandNonEmpty && !(main.doesSneakBypassUse(...) && off.doesSneakBypassUse(...))` (172-205). On Forge/NeoForge, sneaking with items that bypass on both hands does reach the block. "Sneaking with an item never reaches the block" (§1.1, rec. 7) holds for vanilla and Fabric only. Fabric API `UseBlockCallback` runs before all of this [not checked].
4. The client stops the hand loop on FAIL too. [javap V120/V121 `Minecraft.startUseItem` offset 346] on a block hit, `FAIL` returns without trying the off hand, the same as `consumesAction`. The neutral `onUse` can return FAIL on the client to suppress the off-hand packet. The dossier's trap at §1.1 only mentions PASS vs SUCCESS.
5. The client load path exists even without sync code. With a non-empty `getUpdateTag`, the chunk packet makes the client call `load` / `loadWithComponents` / Forge `handleUpdateTag` (C8 evidence). If the plan ever adds `getUpdateTag`, `readData` must treat absent keys as defaults and the base must also route the 1.20.1 client path. Today the empty tag is nulled, so nothing happens.
6. Block class naming. [javap V120, F120, V121 `Block.<init>` 64-95] when `SharedConstants.IS_RUNNING_IN_IDE`, a concrete class whose simple name does not end in "Block" logs `Logger.error("Block classes should end with Block and {} doesn't.")`; N121 stubs the check (64-70). That would trip `tools/check_log.py`. `ChargerBlock` is safe; abstract bases are never instantiated. Whether the dev runs set the flag: [not checked].
7. `Container.stillValidBlockEntity` has a neutral 2-arg form only. [javap V120] 3rd overload `(BlockEntity, Player, int)`, [javap V121] `(BlockEntity, Player, float)`: only `stillValidBlockEntity(BlockEntity, Player)` may be used in directive-free code.
8. Runtime use of the inherited `Block.CODEC` on 1.21.1 (a subclass reporting `Block.CODEC` from `codec()`) was not checked by the dossier or here. The first-task proof (an empty block registered and GameTested on four variants) must cover it; a block-type dump or datagen would expose a mismatch.
